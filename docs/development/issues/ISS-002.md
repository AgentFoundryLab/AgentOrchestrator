# ISS-002: Gemini capability drift vs the validated baseline

> Root-cause work item. Carried forward from `I-002`; see `../ID-MAP.md`.

## Classification

- Category / scope / type: `bugfix` / `installer` / `config`
- Severity: `High`
- Root-cause state: `Suspected`
- Root cause: the Gemini capability profile in the runtime registry diverges from the behavior the installer actually produces, so the declared baseline and the emitted artifacts disagree.

## Status

`Open` — reopened 2026-02-24 after live runtime validation failures in Gemini CLI command loading. Previously marked closed on the strength of the declared baseline rather than observed behavior, which is why the root-cause state is `Suspected` and not `Confirmed`.

## Links

- Affected requirements: `AC-001.1`, `AC-002.1`, `TR-004`, `TRC-004.2`, `TRC-004.3`

## Diagnosis

The registry declares Gemini's capability set; the installer's transform produces the artifacts. Those two are separately maintained, so a change to either can leave the other stating something untrue — and the conformance tests were asserting the declared baseline rather than the loader's acceptance of the output. A profile that says "skills supported" passes a test that only checks the file landed, while Gemini's own loader rejects it.

`REG-002` carries the concrete loader failures.

## Remediation

Bring the declared profile, the transform output, and the conformance assertions into agreement, with the loader's acceptance as the authority rather than the declaration. Do not close on the declaration a second time: closure requires Gemini's own loader accepting every emitted file.
