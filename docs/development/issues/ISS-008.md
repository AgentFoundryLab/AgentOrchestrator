# ISS-008: Installer relies on GNU-only sed and awk syntax

## Classification

- Category / scope / type: `bugfix` / `installer` / `portability`
- Severity: `High`
- Root-cause state: `Confirmed`
- Root cause: Two call sites used GNU extensions rather than POSIX syntax — `sed -i` with no backup suffix, and an `awk -v` assignment carrying a multi-line value. Both are accepted by the GNU/mawk toolchain the CI runner provides and rejected by other conforming implementations, so the defect was invisible to every gate.

> `portability` extends the `issueType` vocabulary, which previously held only `config` and `logic`.
> Neither classifies a platform-syntax defect: the code was configured correctly and its logic was
> right, but its utility syntax was non-portable.

## Status

`Closed` — found 2026-08-14 while deploying the working tree to a macOS host; fixed and verified the same day.

## Diagnosis

`TRC-001.1` requires the installer to operate with "shell and standard POSIX utilities alone". Both
call sites used sed and awk, so the dependency set was correct; the *syntax* was not portable.

**`sed -i` without a backup suffix** (`apply_frontmatter_name_override`, `convert_args_placeholder`).
GNU sed treats `-i`'s argument as optional. BSD sed requires it, so `sed -i <script> <file>` parses
the script as the backup suffix and the path as the script, failing with `invalid command code`.

**A multi-line value passed through `awk -v`** (`inject_policy_refs`). POSIX leaves a literal newline
in a `-v` assignment undefined. gawk, mawk and busybox awk accept it; `original-awk` (BWK awk — what
macOS ships, and a `update-alternatives` option on Debian) rejects it with `newline in string`.

The second failure was the more damaging one. `set -e` is active, so the awk failure aborted the
installer mid-run, after artifacts were written and before the summary — a silent partial install with
exit status lost to the enclosing pipeline. It reached only the *replace* path, when a doc file's refs
block already existed and needed updating; the *append* path on a fresh host worked, which is why the
defect survived first-install testing.

Measured across implementations, same working tree:

| Host + awk | Before | After |
|---|---|---|
| Linux + mawk (CI default) | 50/50 | 50/50 |
| Linux + gawk | 50/50 | 50/50 |
| Linux + `original-awk` | 48/50 | 50/50 |
| macOS + BSD awk/sed | 38/50 | 50/50 |

The two green rows are the whole reason this shipped: CI runs `ubuntu-latest`, whose `awk` is mawk and
whose `sed` is GNU. The gate tested one implementation of each and reported portability it had not
measured.

## Remediation

Replace both constructs with POSIX-conforming equivalents:

- `sed_in_place` — a single helper writing through a temp file, matching the existing
  `strip_claude_frontmatter` idiom, rather than duplicating temp/mv logic at each caller.
- `ENVIRON["ORCH_REFS_BLOCK"]` — pass the multi-line block through the environment, which POSIX
  mandates and all four awk implementations honour.

Verified two ways: the suite passing on each host/awk combination above, and a 20-variant A/B of the
installed trees (five runtimes × `""`/`--namespace`/`--profile commands`/`--hooks`) confirming
byte-identical output before and after on Linux — the fix changes no behaviour where the old code
already worked.

Close the gate gap with CI legs that exercise a second OS and a second awk, so a GNU-only construct
fails the build instead of reaching a host.
