# TD-001: OpenCode hooks are out of scope by policy

> Accepted platform gap with a policy decision behind it. Carried forward from `G-001`; see `../ID-MAP.md`.

## Classification

- Category / scope: `infra` / `hooks`
- Severity: `Low`
- Priority: `P2`

## Status

`Deferred` — accepted, non-terminal. The gap stays registered because the decision could be revisited if OpenCode's plugin model changes.

## Links

- Governing blueprint: `FBP-FND-005` (hook system), `FBP-FND-002` (container)
- Affected requirements: `AC-003.6`, `TRC-004.3`
- Related decision: `docs/knowledge/decisions/non-claude-hooks-policy.md`

## Drift

`FBP-FND-005` describes five lifecycle hook scripts driven by a shell execution model. OpenCode's plugin model subscribes to events through JavaScript or TypeScript plugins rather than executing shell scripts, so the shipped hook scripts have no equivalent there.

The installer reports this as a `GAP` row rather than writing hook files OpenCode cannot execute.

## Why it exists

Deliberate. Emulating the shell hook model in an OpenCode plugin would mean maintaining a second hook implementation for one runtime, and the hooks are reminders rather than enforcement — their absence degrades the experience without breaking any workflow. `TRC-004.3` makes reporting the gap the correct behavior, so this is a documented boundary, not an unfinished port.

## Removal trigger

Either of:

- OpenCode gains a shell-executable hook model, at which point the existing scripts apply directly.
- A hook stops being purely advisory and becomes load-bearing for a gate, at which point its absence on any runtime becomes a correctness gap rather than a UX one.

## Remediation

If triggered: author OpenCode plugin equivalents for the five events, add them to the container blueprint's per-runtime capability table, and extend the conformance suite to assert their presence — mirroring how Claude's hooks are asserted today.
