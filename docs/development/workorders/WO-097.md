# WO-097: Align Gemini capability flags with the validated baseline

## Summary

Bring the installer's Gemini behavior back in line with the documented capability baseline — skills and
subagents supported, hooks excluded by policy — and fix the command-file transform that fails Gemini's
own loader validation.

Implementation Plan: None required.

## In Scope

- Gemini capability flags in the runtime registry
- Gemini install paths for skills and subagents
- The command-file transform that produces Gemini-loadable output
- Conformance tests asserting the Gemini baseline

## Out of Scope

- Gemini hook support — excluded by policy, recorded in `TD-001`'s sibling decision for OpenCode and in the non-Claude hooks policy
- Any other runtime's capability profile

## Requirements

| Requirement | In scope here (brief) |
| --- | --- |
| `AC-001.1` | Agents must install to every supported runtime root, Gemini included |
| `AC-002.1` | Skills must install to the Gemini root with a valid transform |
| `TR-004` / `TRC-004.2` | Installed artifacts must conform to Gemini's own frontmatter and path conventions |
| `TRC-004.3` | An unsupported capability must be reported as a gap, never emulated with an unparseable file |

## Blueprints

- `FBP-FND-002` — Container blueprint: the per-runtime path registry and transform contract

## Test Plan

### Unit Tests

- The transform emits frontmatter Gemini's loader accepts, with unsupported keys stripped rather than passed through.

### Integration Tests

- Gemini skills and subagents land at their expected paths; hooks are absent.
- Uninstalling Gemini leaves every other runtime untouched.

### E2E Tests

- `bash tests/install/smoke.sh` — the Gemini conformance, namespacing, and uninstall-isolation cases pass.

## Linked Feedback

- `ISS-002` — Gemini capability drift, the root cause this Work Order remediates.
