# ADR-012: Governance Rationalization

**Status**: Accepted
**Date**: 2026-02-19
**Context**: Policy overlap, dead files, naming collisions between global and project tiers

---

## Context

AgentOrchestrator's policy structure had accumulated several problems:

1. **Duplication**: `docs/policy/RULES.md` (323 lines) was a superset of `package/policy/RULES.md` (115 lines) — first 115 lines identical, rest was elaboration
2. **Dead files**: Neither `docs/policy/RULES.md` nor `docs/policy/GUIDELINES.md` were loaded into agent context
3. **Naming collision**: Both tiers used `RULES.md`, making it unclear which rules applied where
4. **Missing onboarding**: No skill existed to generate project-specific policies from codebase analysis

The three-tier structure (global → orchestrator-specific → project template) created confusion about what to put where.

## Decision

**Rationalize to two tiers with distinct names**:

### Global (framework-level, auto-loaded)
```
~/.claude/policy/
├── PRINCIPLES.md    # WHY — universal SW philosophy
└── RULES.md         # HOW agents work — orchestrator behavioral rules
```

### Project (project-specific, generated by /onboard)
```
<project>/docs/policy/
├── STANDARDS.md     # WHAT patterns — technical standards, stack conventions
└── GUIDELINES.md    # HOW this project operates — testing, review, deployment
```

### Key changes:
- **Deleted** `docs/policy/RULES.md` (duplicate of global, never loaded)
- **Created** `docs/policy/STANDARDS.md` (orchestrator-specific technical standards)
- **Renamed** project template `RULES.md` → `STANDARDS.md`
- **Created** `/onboard` skill to dynamically generate project policies from codebase analysis
- **Light governance**: Version headers with semver + amendment notes on generated files

## Rationale

### Why rename to STANDARDS + GUIDELINES?
- Eliminates naming collision with global RULES.md
- Clearer semantic distinction: standards (technical what) vs guidelines (process how)
- Neither name conflicts with the framework-level PRINCIPLES or RULES

### Why delete docs/policy/RULES.md?
- First 115 lines were verbatim duplicates of global RULES.md
- Remaining 208 lines were elaboration never loaded into any context
- Useful orchestrator-specific content moved to STANDARDS.md

### Why /onboard instead of static templates?
- Static templates produce generic placeholder files
- /onboard analyzes actual codebase to derive relevant standards
- Brownfield projects benefit from convention detection
- Standards are evidence-based, not aspirational

### Why version headers?
- Lightweight governance without bureaucratic overhead
- Semver communicates change impact
- Amendment notes provide rationale trail

## Alternatives Considered

### Alternative 1: Constitution Approach
Create a formal "constitution" with hardcoded articles for all projects.

**Rejected**: Too rigid. Projects have vastly different needs. Static articles become stale or irrelevant.

### Alternative 2: Keep Three Tiers
Maintain global → orchestrator → project template structure.

**Rejected**: The orchestrator-specific tier (docs/policy/) was never loaded and duplicated global content. Two tiers is sufficient.

### Alternative 3: Merge Everything into Global
Move all rules into global RULES.md.

**Rejected**: Global rules should be universal. Project-specific standards don't belong in a framework-level file.

## Consequences

### Positive
- Clear separation: framework rules (global) vs project standards (local)
- No naming collisions between tiers
- /onboard generates useful, project-specific content
- Version headers enable lightweight change tracking
- Dead files eliminated

### Negative
- Existing projects using `docs/policy/RULES.md` need migration
- /onboard requires codebase to have enough signals for meaningful standards

### Mitigations
- Project template provides starting point if /onboard insufficient
- install.sh updated to deploy new template names
